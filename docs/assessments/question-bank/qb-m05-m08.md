## Q1 — Truth table with a discriminating row

**Module 5 · CLO-5 · Difficulty 2/4 · Type: Data representation exercise**

Build the truth table for `(A AND NOT B) OR C` and state which single row distinguishes it from `A OR C`.

<details>
<summary>Model answer</summary>

Rows (A,B,C → out): 000→0, 001→1, 010→0, 011→1, 100→1, 101→1, 110→0, 111→1. The discriminating row is **A=1, B=1, C=0**: `(A∧¬B)∨C` = 0 but `A∨C` = 1 — everywhere else the two agree. A good answer shows intermediate columns (¬B, A∧¬B) as the method, not just the final column.
</details>

## Q2 — NAND builds everything

**Module 5 · CLO-5 · Difficulty 3/4 · Type: Conceptual**

Using only NAND gates, construct NOT, AND, and OR (truth-table-level justification for one of them).

<details>
<summary>Model answer</summary>

NOT: tie both inputs to A — `NAND(A,A) = ¬(A∧A) = ¬A`. AND: `NAND(A,B)` gives `¬(A∧B)`; feed that through the NOT construction → `A∧B`. OR: by De Morgan, `A∨B = ¬(¬A∧¬B)` — so `NAND(NAND(A,A), NAND(B,B))` (NOT each input, then NAND the results). Justification for OR: with A=1: ¬A=0, so NAND(0, ¬B) = ¬(0∧¬B) = 1 regardless of B ✓; with A=0: NAND(0,¬B)... recompute — NAND(¬0, ¬B) = NAND(1, ¬B) = ¬(1∧¬B) = ¬¬B = B ✓ — output follows B, exactly OR's behaviour. The insight: **NAND's universality is why whole chips were historically built from NAND gates**.
</details>

## Q3 — Half adder roles

**Module 5 · CLO-5 · Difficulty 2/4 · Type: Short answer**

A half adder has inputs A, B and outputs SUM, CARRY. Give each output's Boolean expression, and explain why chaining half adders is not enough to add multi-bit numbers.

<details>
<summary>Model answer</summary>

SUM = A XOR B; CARRY = A AND B. Chaining limit: a half adder has no **carry-in** input — when adding bit position n, the carry from position n−1 must participate; two half adders + an OR of the carries (or XOR for the sum path) make the **full adder**. The one-sentence diagnosis: multi-bit addition is a *ripple of carries*, and a circuit without a carry input cannot ripple.
</details>

## Q4 — The absolute-reference fix

**Module 5 · CLO-5 · Difficulty 2/4 · Type: Troubleshooting**

A grading spreadsheet computes `=B2*$H$1` down a column. A colleague's version uses `=B2*H1` and breaks when copied down. Diagnose what goes wrong and state the general rule.

<details>
<summary>Model answer</summary>

Without `$`, the reference is *relative*: copying down shifts it row-by-row (B3×H2, B4×H3…), so rows below the first multiply by empty/wrong cells. `$H$1` is *absolute* — locked on both axes — so every row multiplies the same constant (the grade boundary or weight cell). General rule: lock what should not move (`$` before column and/or row as needed), leave relative what *should* follow the fill direction; mixed refs (`H$1`, `$H1`) lock exactly one axis.
</details>

## Q5 — The chart that shouts

**Module 5 · CLO-5 · Difficulty 3/4 · Type: Comparative**

A club's poster chart shows membership "doubling" — but the y-axis starts at 40, not 0, and the two bars are 47 vs 52. Redesign it honestly and write the caption.

<details>
<summary>Model answer</summary>

Redesign: bar chart with y-axis **from 0**, both bars labelled with their values (47, 52); if the story is *change*, use the delta explicitly (52−47 = +5 members, ~11% growth) rather than visual amplification. Caption: "Membership grew from 47 (2025) to 52 (2026) — +5 members (+11%)." The principle: the axis choice is a *rhetorical* choice; truncating it manufactures drama the data doesn't support. A good answer names why the original is misleading (bar length encodes magnitude — a truncated axis breaks that encoding) and keeps the honest redesign equally simple.
</details>

## Q6 — Delegation with deadlines

**Module 5 · CLO-5 · Difficulty 3/4 · Type: Scenario-based**

Five-person group project, one week out: one member's laptop can't run the presentation software, two have cloud accounts, one has only a phone. Design the workflow so nobody is blocked, and the contingency for the day the strong laptop dies.

<details>
<summary>Model answer</summary>

Workflow: **browser-based editors** for slides and report (old laptop and phone can review/comment even if authoring is uncomfortable); cloud folder with **per-section files, one named owner each** (version history attributes edits for fair grading); the phone member gets reviewing/testing roles early plus authoring sprints on campus machines. Contingency: because everything already lives in the cloud, the strong laptop is just a terminal — any member's account can present; refresh a USB export before each milestone for the venue-with-no-Wi-Fi case. Marks: the design makes the weakest device *productive*, and the contingency is trivial **because the architecture already survived the laptop dying** — no deliverable ever lived on it.
</details>

## Q7 — Trace the web request

**Module 6 · CLO-7 · Difficulty 3/4 · Type: Conceptual**

You type `portal.university.edu` and press Enter. Trace what happens in order: DNS, TCP, TLS, HTTP — one sentence each, plus the one step where an attacker on café Wi-Fi could have intercepted traffic if the site were plain HTTP.

<details>
<summary>Model answer</summary>

**DNS:** the browser asks a resolver to translate the name to an IP (cache → recursive resolver → authoritative chain). **TCP:** a connection to that IP:443 is established (three-way handshake) — reliable, ordered delivery. **TLS:** certificate verification (is this really the university's server?) + key exchange → encrypted channel. **HTTP:** the request (`GET /`) and response (status, headers, page) travel *inside* the TLS tunnel. Interception point if plain HTTP: any hop on the path — the café's router or any ISP between you and the server can read (and alter) the traffic, since HTTP has neither encryption nor server authentication. A good answer puts DNS *before* TCP (you can't connect to a name) and names the HTTP failure as *both* confidentiality and integrity loss.
</details>

## Q8 — Bandwidth vs latency

**Module 6 · CLO-7 · Difficulty 2/4 · Type: Comparative**

A video call lags while a large backup hums along fine in the background. Which parameter is hurting the call, and why doesn't the backup care as much?

<details>
<summary>Model answer</summary>

The call is hurt by **latency/jitter** (and packet loss) — it's interactive: audio/video must arrive within tens of milliseconds or the conversation breaks; it also needs modest but *steady* bandwidth. The backup cares about **throughput over time** — it can tolerate delay (it's not interactive), so it just fills available bandwidth slowly. Why they conflict: the backup's greed can fill queues, adding latency to the call's small packets (bufferbloat-class effect). A good answer names which parameter each application *needs* rather than just "the internet is slow".
</details>

## Q9 — Three workloads, three cloud models

**Module 6 · CLO-7 · Difficulty 3/4 · Type: Comparative**

Assign: a research team analyzing a large public dataset; a student writing an essay in a browser; a company migrating its legacy inventory system. Name the cloud service model for each and one responsibility the *renter* keeps in each.

<details>
<summary>Model answer</summary>

Dataset analysis → **IaaS** (virtual machines/storage rented; renter keeps OS hardening, patching, and access control). Essay in a browser → **SaaS** (complete application consumed; renter keeps *data* — sharing settings, account security, what they store where). Legacy system migration → **PaaS** (a managed runtime to rebuild into; renter keeps application code, its bugs, and its data governance). A good answer states the gradient (who manages what) rather than the acronyms alone — and notes "the cloud" is not one thing.
</details>

## Q10 — The padlock that proves nothing

**Module 6 · CLO-7 · Difficulty 2/4 · Type: Networking & cybersecurity scenarios**

A scholarship site has a valid padlock but asks for an application "processing fee" by gift card. The URL is `university-scholarships-apply.com`. Give the two-sentence triage you'd teach a friend.

<details>
<summary>Model answer</summary>

The padlock certifies the *connection* is encrypted to *that domain* — it says nothing about who runs the domain or whether they're honest. Two checks settle it: does the university's own site (typed by hand, not via this link) list this scholarship, and does any legitimate scholarship ever demand gift-card fees or urgency? (No.) Report the site through the university's phishing channel; the lookalike domain is the tell the padlock was designed to distract from.
</details>

## Q11 — Schema reading

**Module 7 · CLO-8 · Difficulty 2/4 · Type: Short answer**

`STUDENTS(student_id PK, name, programme)` and `ENROLMENTS(student_id FK, course_code, term, grade)`. What does the FK prevent, and what question does the pair answer that one big sheet couldn't?

<details>
<summary>Model answer</summary>

The foreign key prevents **orphan enrolments** — an enrolment naming a student who doesn't exist in STUDENTS cannot be inserted (referential integrity); it also blocks deleting a student while their enrolments reference them (in the default restrict mode). The pair answers, structurally and in seconds: "who took what, when, and how did they do?" — a join on student_id filters by any combination (programme + term + course), while one big sheet with repeated student rows cannot *guarantee* consistency (typos create phantom students) and must be re-scanned by eye for every question.
</details>

## Q12 — The query in plain English

**Module 7 · CLO-8 · Difficulty 2/4 · Type: Short answer**

```sql
SELECT name FROM students
JOIN enrolments ON students.student_id = enrolments.student_id
WHERE term = 'Autumn' AND grade IS NULL;
```

State, in plain English, what this returns — and what `grade IS NULL` means (and does not mean).

<details>
<summary>Model answer</summary>

Plain English: "the names of students who have an Autumn-term enrolment with **no grade recorded yet**." `IS NULL` tests for the *absence of a value* — it is not zero, not empty string, not "failed"; those are values. The subtlety it must not mean: "students with no grades at all" (they might have other graded enrolments) — the query scopes to the Autumn rows only. A good answer notes NULL requires `IS`, not `=` — `grade = NULL` matches nothing.
</details>

## Q13 — Where the pipeline broke

**Module 7 · CLO-8 · Difficulty 3/4 · Type: Troubleshooting**

A data team's monthly report suddenly shows half the usual sales. The dashboard queries are unchanged. Name three places the break could be, in diagnostic order, with the first check for each.

<details>
<summary>Model answer</summary>

(1) **Upstream data** — the source system changed (timezone switch, partial export, a new "test" flag filtering rows); first check: row counts by day at the source, comparing to last month. (2) **The load/transform step** — a scheduled job failed or silently truncated (schema change upstream, mapping not updated); first check: job logs and loaded-vs-source counts. (3) **The query's assumptions** — a dimension change (e.g., a renamed region value now excluded by a WHERE clause); first check: run one unchanged control query on an unaffected segment. Order rationale: check from the source *forward* — each stage inherits the previous stage's problems, so a clean source eliminates half the tree first.
</details>

## Q14 — The dataset that changed meaning

**Module 7 · CLO-8 · Difficulty 4/4 · Type: Extended problem-solving**

A two-year air-quality study: year two's "30% improvement" coincides with the city *silently relocating sensors* (note buried in a PDF appendix). State what the team's draft conclusion got wrong, the redesign that salvages the analysis, and the exact claim the evidence now supports.

<details>
<summary>Model answer</summary>

Wrong: the draft attributed to *policy* what the relocation explains — sensor placement (kerbside vs parkside) changes readings systematically, so the improvement may be a measurement artefact; the same series break applies to the quiet *model* change. Redesign: analyse only the **overlap window** (both sensor generations running), use neighbouring cities as control series, report raw *and* break-adjusted trends, and state limitations prominently. Supported claim: "a decline coinciding with the sensor transition is observed; attribution to policy is **not supported** by comparable measurements." The grade is in the calibration — claiming neither the original conclusion nor its opposite (absence of support is not evidence of reversal).
</details>

## Q15 — Threat or trick question

**Module 8 · CLO-10 · Difficulty 1/4 · Type: Multiple choice (with why)**

Which statement about ransomware is most accurate?

- A) It is a virus that deletes files immediately.
- B) It encrypts files (or locks systems) and demands payment; infection commonly arrives via phishing links/attachments or exposed remote-access services.
- C) It only targets large companies; students are safe.
- D) Antivirus makes backups unnecessary.

<details>
<summary>Model answer</summary>

**B.** The defining behaviour is *extortion via denial of access to data* (encryption, or locking, with the modern twist of also threatening to leak stolen data), and the delivery paths named are the statistically dominant ones — phishing for the initial access, exposed remote services for automation. A is wrong on behaviour (deletion defeats the extortion), C is empirically false (schools, hospitals, individuals' machines are all targets), D confuses prevention with recovery — backups are what make ransomware survivable; AV reduces but never eliminates infection.
</details>

## Q16 — The MFA question that isn't a trap

**Module 8 · CLO-10 · Difficulty 2/4 · Type: Conceptual**

An attacker has your password from a breach list. Name the three MFA factor categories, say which two categories your bank app's approval prompt uses, and explain why the phished password alone now fails.

<details>
<summary>Model answer</summary>

Categories: **something you know** (password/PIN), **something you have** (phone/app/security key), **something you are** (fingerprint/face). The bank app prompt uses *have* (the registered phone) + *are* (biometric unlock of the app) — layered on *know* (the password you typed). Why the password alone fails: possession of the password is only one of the categories — the attacker must also steal the second factor in real time, which is exactly what phishing kits increasingly try to do (real-time relay), hence push-bombing awareness and number-matching prompts. Good answers name the category *structure*, not just examples.
</details>

## Q17 — Privacy triage on a form

**Module 8 · CLO-10 · Difficulty 3/4 · Type: Scenario-based**

A society's event form collects: name, email, student ID, dietary needs, and "any accessibility requirements", in a spreadsheet shared with four organizers, retained indefinitely. Apply three data-protection principles and redesign.

<details>
<summary>Model answer</summary>

Principles: **minimization** (collect only what the event needs — student ID is not needed to order pizza; accessibility requirements *are* needed, and sensitive), **access limitation** (four organizers see everything, including health-adjacent disclosures — need-to-know fails), **retention limits** ("indefinitely" has no purpose). Redesign: name + email + dietary needs + an optional accessibility field handled by one designated organizer; retention: delete the sheet after the event term; access: the sensitivity column restricted (or collected via direct contact instead of the form). A good answer keeps accessibility support *available* while shrinking its exposure — the fix is design, not deletion of support.
</details>

## Q18 — Decompose the problem

**Module 8 · CLO-9 · Difficulty 3/4 · Type: Extended problem-solving**

"Compute each student's course grade: best 10 of 14 quiz scores, scaled to 15%, added to lab 20%, midterm 20%, project 25%, final 20%." Decompose into sub-problems and write the pseudocode for the quiz aggregation.

<details>
<summary>Model answer</summary>

Decomposition: (1) read/validate inputs (scores 0–max, presence); (2) quiz aggregation: sort desc → take first 10 → sum → scale to 15% weight; (3) weighted combination of components; (4) output (per-student grade + sanity bounds). Pseudocode:

```
scores ← list of 14 quiz scores        # validate each 0..max
sort scores descending
top10 ← first 10 of scores
quiz_pct ← sum(top10) / (10 × max)     # 0..1
final_pct ← 0.15×quiz_pct + 0.20×lab_pct + 0.20×mid_pct
          + 0.25×proj_pct + 0.20×fin_pct
```

A good answer names the *edge cases* the decomposition exposes (absences → fewer than 10 scores? cap at available), which is exactly why decomposition precedes coding.
</details>

## Q19 — Evaluate the AI claim

**Module 8 · CLO-10 · Difficulty 3/4 · Type: Comparative**

An AI study-tool claims "95% accurate answers". A classmate trusts it for citations. Give the two questions that expose the claim's weakness and the verification order you'd recommend for its output.

<details>
<summary>Model answer</summary>

Two questions: **95% of what?** (accuracy measured on what distribution — fluent explanations are easy; niche citations are where errors concentrate) and **what does the 5% cost?** (a wrong citation poisons the reader's trust budget and the student's grade; error *consequences* are asymmetric, not uniform). Verification order: **citations and numbers first** (fastest to falsify, most damaging when wrong), then definitions, then explanations; mark what couldn't be verified as unverifiable; disclose use. A good answer refuses both "AI is useless" and "95% is great" — the distribution and the stakes decide.
</details>

## Q20 — The stuck flag

**Module 8 · CLO-10 · Difficulty 3/4 · Type: Troubleshooting**

A lab door unlocks when `card_valid AND (PIN OR supervisor) AND NOT lockout`. One Friday, lockout is ON but the supervisor flag stuck ON from Thursday. Evaluate the expression; state the verdict and the flag-hygiene rule.

<details>
<summary>Model answer</summary>

Evaluation: `NOT lockout` = false, so the whole AND-chain is **false — the door must not open**, regardless of the stuck supervisor flag. Verdict: if it *did* open, the implementation doesn't match the expression — the wiring/config is the investigation, not the algebra. Flag hygiene: a flag consumed by a security decision must be **fresh** — re-asserted (heartbeat, badge-tap) or expiring; stale state silently rewrites policy. The deeper habit: evaluate the stated rule *before* trusting the mechanism — Friday is exactly that check.
</details>

## Q21 — Open-verdict case: the energy dashboard

**Module 8 · CLO-9 · Difficulty 4/4 · Type: Extended problem-solving**

A dorm's live energy dashboard cut usage 9% in month one; by month three usage was back to baseline. The pilot report recommends "more dashboards". Diagnose three candidate mechanisms, name the test that discriminates, and evaluate the recommendation.

<details>
<summary>Model answer</summary>

*(Open-verdict: multiple defensible diagnoses, marks for mechanism + discriminating test.)* Candidates: (1) **novelty decay** — passive displays fade once seen; (2) **confound** — weather/exams changed (usage would have risen anyway); (3) **feedback absence** — the display showed numbers with no *actionable* loop (no floor goal, no comparison, no "what do I do?"). Discriminating tests: weather-normalize and compare to non-pilot dorms (kills/confirms the confound); interview residents ("did you know what to do with the number?") (tests feedback absence); re-engagement events pausing the decay (tests novelty). Evaluation of "more dashboards": it replicates the *input* without addressing the *mechanism* — likely replicates the decay too; the defensible recommendation targets the diagnosed cause (e.g., social comparison + actionable framing + re-engagement), with a measurement plan pre-committed so next term's report can't fool itself either.
</details>

## Q22 — Two-town broadband trade

**Module 8 · CLO-9 · Difficulty 4/4 · Type: Extended problem-solving**

A regional government can afford one town properly: Town A (dense, ISPs willing to co-invest) or Town B (scattered, higher unserved rate, community initiative recently collapsed in debt). State the criterion that should decide it, design each town's intervention (they may differ), and name the quality trade the loser accepts.

<details>
<summary>Model answer</summary>

*(Open-verdict: strong answers argue, weak answers pick.)* Deciding criterion: the programme's own mandate metric — **unserved households connected per unit subsidy** (B's scatter is expensive but its unserved rate is higher; A's density means ISP co-investment does the work cheaply). Defensible designs: **A = subsidized fixed-line** (density economics; modest public subsidy per household); **B = community-owned fixed-wireless with the governance reforms the collapse implies** (grant-funded, public accounts, elected oversight — trust damage is a *design constraint*, so no pre-payment). Trade named: A's gigabit-class quality exceeds B's reliable-100Mbps-class — acceptable because the access *floor* is guaranteed in both towns and the mandate counts unserved households, not speed tiers. Marks: criterion explicit; the B design *changes because of* the trust history; the quality trade is stated, not hidden.
</details>

## Q23 — The course looking at itself

**Module 8 · CLO-9 · Difficulty 4/4 · Type: Extended problem-solving**

Next year's case bank should be student-maintained: each cohort contributes cases, the best are curated in. Name the three failure modes most likely to kill the system by year two and one structural prevention for each.

<details>
<summary>Model answer</summary>

*(Open-verdict: marks for named failure modes + *structural* preventions.)* (1) **Quality collapse** — unscaffolded contributions are quizzes or insider-knowledge riddles → prevention: the submission *is* the validated template (machine-checked fields) plus a "solvable-and-grounded" test reviewed at curation. (2) **Privacy/consent incidents** — real people/employers in scenarios → prevention: structural sanitization rules (fictionalization checklist at curation), not honor-system. (3) **Metadata decay + curator burnout** — level/domain fields drift, backlog grows, contributions stop: *the system dies of maintenance* → prevention: validator-enforced metadata + two-deep curator rota with credit-bearing roles. A good answer notices the recursion: the bank must apply the course's own principles (validation, separation, succession) to itself.
</details>
