## PB-301 — Choosing the department's shared laptop pool

**Solution guide.** Criteria first (weights shown, summing to 100%): durability/uptime in shared use (30%), maintenance simplicity — single model, one technician (20%), student-hours delivered (count × reliability, not just count) (20%), spare/accessory availability (15%), cost ceiling respected (15%). Scoring: "cheapest ×10" scores high on count but collapses on durability and single-model service; "6 premium" maximizes per-machine quality but delivers fewer student-hours and 4 machines of dead capital; "8 mid-range + accessories" usually scores best because accessories (bags, locks, spare chargers) are *reliability multipliers* — they protect the 4-year uptime the criteria actually pay for. The insight weak answers miss: the technician can service one model fast and three models badly — fleet homogeneity is an uptime feature, not an aesthetic. The flip-fact must be named: "if usage is mostly staff presentations, 6 premium machines win — few machines, high polish, low abuse."
**Alternatives.** 6-good + 4-reserve is defensible if the technician can't handle mid-range failure volume (check their honest capacity); leasing (often excluded by grant rules — say so).
**Trade-offs.** Machine count vs per-machine quality; upfront accessories (unsexy spend) vs warranty claims later; standardization vs negotiating multi-vendor discounts.
**Common mistakes.** Counting machines instead of student-hours (a dead laptop delivers zero); no weights (a list is not a criteria set); hidden assumptions about abuse rates; no flip-fact (the recommendation reads as taste, not analysis).

## PB-302 — The department's drive fills every October

**Solution guide.** Root cause: capacity is managed *reactively* — no ownership, no lifecycle, no tiers — so "delete stuff" is the policy by default, and it eventually ate an unbacked archive. The policy has one mechanism per problem: **prevention** — per-folder quotas with a named owner per folder (storage growth gets a budget like money does); **triage** — an annual archival tier (compressed, cold storage) so "superseded" stops meaning "delete-worthy"; **recovery** — versioned snapshots so deletion is reversible. The archive died because no tier existed between live and delete — the archival tier *is* the fix; the lecturer's materials would have compressed down and waited. The flag the prompt demands: retention/compliance rules are **unknown** — a good answer *asks the registrar* before any deletion policy is enforced; assuming compliance is exactly the failure mode the flag prevents.
**Alternatives.** Buy more storage (defensible in the short term; treats the symptom — October returns, bigger); move video to a streaming platform (genuinely good for the dominant content class; doesn't fix governance for the rest).
**Trade-offs.** Quota enforcement (fairness across folders) vs admin effort (per-folder owners take cultivation); archival tier cost (small) vs the deletion risk it retires.
**Common mistakes.** Root cause = "users keep too much" (blame is not a mechanism — test it: measure what classes of content actually fill the drive; videos, not hoarding); quota-first implementation (it repeats the reactive pattern with a leash); no owner per folder (quotas without owners become nobody's job); skipping the compliance flag.

## PB-303 — The three-way format standoff

**Solution guide.** The strategy table maps each content type to its audiences: reports → working master (editable) + PDF for the funder + PDF/A for the library; spreadsheets → working master + CSV (open, lossless for data) for preservation; photos → working masters + lossless/TIFF-class preservation copies. The key move: duplication is *deliberate, by audience* — not accidental, by history. The 20-year answer: open formats (plain text/CSV, PDF/A, uncompressed images) outlive software dependencies; but format is the *smaller* half — the README (what each file is, what software created it, what it means, dates) is what makes the corpus usable in 2046, because a file without its context is a format problem no conversion solves. Annual ritual: reconvert masters → preservation copies, spot-open ten random files, checksum verify, update the README — sustainable effort, not heroics.
**Alternatives.** Single-master-with-conversion-on-demand (cheaper, but 20-year conversion tooling is a bet); deposit-only-with-library (outsources preservation — defensible if the library accepts masters).
**Trade-offs.** Duplication (storage, sync discipline) vs conversion-on-demand risk; the funder's PDF convenience vs the library's preservation standard (both served by keeping masters + two exports).
**Common mistakes.** Treating "preservation-grade" as exotic tooling (it's open formats + documentation); converting originals and losing editability (the partner lab's need destroyed by the library's); no README (the corpus survives, the *meaning* doesn't); a one-time project with no annual ritual (format rot resumes).

## PB-304 — The exam-hall Wi-Fi that must not fail

**Solution guide.** Diagnosis: the symptom is *dropouts, not slowness*, on lecture-tuned APs with 300 concurrent devices doing bursty traffic — that pattern says **airtime/association contention** (too many devices competing per AP), not backhaul starvation (burst traffic rarely saturates upstream). Decision criteria, named: symptom match (a matches, b doesn't), deployment time before the exam (APs install in days, backhaul in weeks), cost (a is cheaper) → **(a)**. Fallback plan, three elements: (1) verify the quiz platform's client-side save/resync (already exists — *verify*, don't assume); (2) invigilator protocol for reconnect stalls — patient, no mass-retry (a synchronized retry is a second spike); (3) paper backup forms for a declared emergency. The honest hedge: if per-AP load logs later show backhaul saturation, (b) wins — name the measurement that would decide it, because the decision is evidence-bounded, not eternal.
**Alternatives.** Do-both-if-budget-allows (not available — the constraint is one budget); postpone-to-in-person (excluded by scenario — the exam format is fixed).
**Trade-offs.** Symptom-match (airtime) vs future-proofing (backhaul also ages — but you don't buy next year's fix during this year's outage); deployment speed vs depth.
**Common mistakes.** "More bandwidth" as reflex (the dropout pattern contradicts it — use the evidence); no fallback (the quiz's local-save property changes the risk calculus — a good answer notices and uses it); treating the choice as permanent (no hedge/measurement); no criteria — option taste instead of option analysis.

## PB-305 — The spreadsheet that runs the hostel

**Solution guide.** Decision with criteria, not vibes: the concurrency failures (two staff overwriting) and the owner's analytical question ("which rooms make money?") are **structural** — they're properties of single-table design, unfixable by discipline; staff fluency and budget argue for staying. Migrate, because structural problems don't respond to exhortation — but the honest answer states both sides first. Schema: ROOMS (room_id, class, rate), GUESTS (guest_id, contact), BOOKINGS (booking_id, guest_id, room_id, start, end — *the double-booking constraint lives here*, enforceable structurally), PAYMENTS (booking_id, amount, date), REQUESTS, SHIFTS. The insight: "be careful" cannot fix double-booking because the sheet has no way to *say* the constraint; a relational schema can. Migration without downtime: (1) freeze or single-writer rule on the live sheet; (2) export/reshape into entity tables; (3) **parallel run two weeks** — old sheet read-only as the comparison source; (4) cut over after reconciliation; rollback = the frozen sheet, still intact.
**Alternatives.** Stay-with-discipline (defensible if staff genuinely number two and turnover is low — but the double-booking already happened, which is evidence against); spreadsheet-adjacent relational tools (the right middle — "relational-shaped" with forms).
**Trade-offs.** Migration effort (training afternoon + reconciliation) vs recurring failure cost; structural guarantees vs staff comfort — continuity risk managed by parallel run, not avoided.
**Common mistakes.** Schema mirroring the spreadsheet's shape (tables should mirror *facts*, not the old sheet's columns); migrating payments before guests (orphaned keys); no parallel run (the business *is* the data — no cutover without comparison); "be careful" as the double-booking fix (the case's central lesson, missed).

## PB-306 — The phishing simulation dilemma

**Solution guide.** The analysis runs both designs against two axes: (a) realistic-and-tracked maximizes realism but punishes the exact behaviour that defends the organization — research and the backlash precedent both say click-shaming suppresses *reporting* (people hide clicks); it also treats staff as suspects, spending trust. (b) consented-and-aggregated trades realism for engagement and culture; its risk is the complacency gap (announced exercises may miss who'd click a real one). Position: defensible either way — strong answers pick one and argue it against its own worst case. Guardrails regardless: no individual punishment for clicking (the learning must survive the click); a one-click report button, *celebrated*; data aggregated, never person-tracked; varied difficulty across repeat exercises. The deep insight to name: **phishing training's true KPI is report rate, not click rate** — optimize reporting and both trust and defence improve; optimize click-shaming and both degrade.
**Alternatives.** No simulation at all (defensible if reporting culture is already strong — measure first); tabletop exercises (zero deception, weaker realism — a legitimate starting rung).
**Trade-offs.** Realism vs consent; individual accountability (the optics leadership wants) vs the reporting culture (the defence that works); the resentment cost of (a) is a *security* cost, not an HR nicety.
**Common mistakes.** Equating caught-clicks with training success (the KPI inversion — the case's core lesson); surveillance framing ("we'll know who clicked") announcing itself in the design; no guardrails (position without ethics scaffolding); dismissing (b) as unrealistic (announced exercises still measure response paths).

## PB-307 — The 4-year-old phone decision

**Solution guide.** Quantify four options with assumptions stated: keep-as-is (cost: £0; reliability risk: battery dies mid-exam-season — high; security horizon: ends this year); replace-battery (~£40–60; buys 2+ years of battery reliability but the security horizon still ends — sequencing property); buy-used mid-range (~40–60% of new; resets both horizons; its footprint is near-zero *new* embodied carbon); buy-new (highest cost, highest carbon, longest horizon). The decoupling insight: battery and updates fail on *different clocks* — the battery is the near risk (exam season), updates the far risk (security). Because manufacture dominates a phone's footprint, *timing* is the environmental lever: extending this device's life where it's safe beats replacing early. Common defensible decision: **replace battery now (exam security) + buy used when updates end (sequenced, low-carbon, low-cost)** — or used-now with the old phone traded onward (its second life is the footprint argument). The strongest counter-argument ("battery repair delays the inevitable") is answered by sequencing: the repair buys exam security *and* time to buy well rather than rush.
**Alternatives.** New-now (defensible if the update horizon genuinely gates required software — check before asserting); phone-as-hotspot + cheap tablet (non-standard; fine if workload allows).
**Trade-offs.** Money now vs money later; exam-season reliability (non-negotiable, per the constraint) vs environmental preference — sequencing resolves rather than sacrifices.
**Common mistakes.** Treating update-end as instant brick (it's a horizon — apps degrade before it bites); treating battery-replacement as throwing money away (it buys time — the sequencing property); no quantification (values without numbers decide nothing); conceding the counter-argument instead of answering it.

## PB-308 — The group project with unequal laptops

**Solution guide.** Architecture around the weakest link, deliberately: **browser-based editors** for text and slides (the old laptop and the phone can both *review and comment* even if authoring is uncomfortable); cloud folder with **per-section files, one named owner each** — version history attributes edits for fair grading without surveillance (the contribution record is a byproduct of the design, not a monitoring layer); the phone member gets reviewing/testing roles *early* (their device handles it) plus authoring sprints on campus machines — role design makes the constraint productive instead of shameful. Convention: numbered files, dated names, owner in the file. The strong-laptop contingency, three steps: everything already lives in the cloud (the laptop is a terminal — nothing authorizes it as load-bearing); any member's account can present; a USB export is refreshed before each milestone. The insight to name: **the contingency is trivial because the architecture already survived the laptop dying** — redundancy was designed in, not bolted on.
**Alternatives.** Everyone-local + manual merge (the friction the case describes — rejected with reasons); separate tools per member preference (merge chaos — rejected).
**Trade-offs.** Cloud dependency (offline weakness) vs device independence (the case's point) — a pre-meeting download ritual covers the venue-Wi-Fi gap; role equity vs the strong laptop's efficiency.
**Common mistakes.** Designing for the average member (the weak laptop then breaks everything, again); version history ignored as the grading mechanism (surveillance habits creep in instead); contingency = "we'd figure it out"; no owner convention (merge chaos replaces device chaos).

## PB-309 — The smart-meter data request

**Solution guide.** The anonymization claim fails on mechanism: at 15-minute granularity, the *load shape itself* is the identifier — occupancy patterns (nobody home 09:00–17:00, the overnight baseline, the weekend signature) are inferable from consumption curves without any name attached; join a profile to an address (which the utility has by definition) and the "anonymized" dataset re-identifies households. "No names attached" ≠ anonymous — the claim must be tested, not trusted. Minimization as *parameters*, not verdicts: **temporal aggregation** (hourly or daily peaks may serve advice-generation nearly as well — measure the accuracy cost), **spatial aggregation** (neighbourhood-level targeting instead of household), **retention limits** (granular data purged after the model's training window). Go/no-go as testable thresholds: "if advice quality at daily aggregation retains ≥90% of pilot quality, ship the coarser tier" — a *number*, decided in advance, not a vibe after the fact. Boundary honesty: students flag what a real deployment needs (DPIA-class assessment, regulator engagement) without pretending to specify it.
**Alternatives.** Consent-based granular program (opt-in households only — defensible; limits coverage and skews the sample); differential-privacy-style aggregation (conceptually right; heavy machinery for a first-semester analysis — name it, don't implement it).
**Trade-offs.** Advice precision (the project's value) vs re-identification risk (the harm) — the levers price that trade explicitly; legal opinion vs privacy reality (legal said fine; the analysis explains why both can be sincerely held).
**Common mistakes.** Accepting "anonymized" as a label (the case's core test — the mechanism must be *explained*, not dismissed); treating minimization as a verdict ("don't do the project") instead of parameters; go/no-go without thresholds (decisions made after seeing results are rationalized, not reasoned); ignoring the no-interpreter-free baseline (status quo has its own harm).

## PB-310 — The open-book exam under a proctoring tool

**Solution guide.** Capability analysis first: behavioural flags are *indicators, not evidence* — documented false-positive patterns concentrate in movement/gaze variance (neurodivergence), environment diversity (rooms, lighting, camera quality), and benign behaviour (looking away to think); flag ≠ proof, and the cost asymmetry is brutal: a false accusation harms a student far more than a missed violation harms the exam. Policy: **flags → human review of flagged segments only → no automated penalties** — the tool narrows where humans look; it never decides. Appeal design, two properties that make it fair: **fast** (days, not weeks — a slow appeal is a punishment for the wrongly flagged) and **evidence-disclosing** (the student sees the flagged basis and the segment — you can't contest what you can't see). The honest boundary: no policy eliminates the tension; the design *allocates* it — flexibility for the many, review burden for the few, dignity preserved by process rather than promise.
**Alternatives.** In-person halls only (equity costs of its own — travel, health, anxiety; the status quo isn't neutral); no proctoring + open-web design (defensible for some assessments — redesigning the exam is the long-term answer, same as PB-416's insight).
**Trade-offs.** Integrity assurance vs surveillance harm; review burden (staff time) vs false-positive rate (student harm) — the human-review layer is where the university spends money to spend *less* harm.
**Common mistakes.** "The AI is 95% accurate" as the frame (accuracy on *what population*? the base-rate question decides everything); automated penalties anywhere (the asymmetry veto); slow/secret appeals (both properties violated); treating the two student factions as obstacles rather than the policy's design inputs.

## PB-311 — The library's dying catalogue terminal

**Solution guide.** Criteria table (weights shown): security (35%), downtime risk (25%), cost (20%), longevity (20%). (a) Replace now: security ✓✓, downtime low (staged cutover), cost high (book budget), longevity ✓✓. (b) Isolate: security ✓ short-term (the remote surface shrinks to the catalogue server) but *decays* — an unpatched OS ages badly even isolated (removable-media, local exploits, app-update needs), and the decay accelerates; (c) lighter OS: best longevity-per-dollar, moderate staging effort. Common strong recommendation: **(c) staged on the spare machine, with (b)-style isolation as interim hardening** — the spare enables parallel-run, the isolation buys time, the migration ends the decay. Transition plan that answers the librarian's *fear* (downtime) rather than dismissing it: stage on the spare → parallel-run one week (both terminals live, patrons switch naturally) → cutover in a low-peak window (usage peaks after school) → old terminal kept as fallback for a month. Her fear is designed against — the plan *is* the answer, not a reassurance.
**Alternatives.** (a) now (defensible if budget allows without book cuts — say which); (b) alone (defensible only with a *sunset date* — isolation without expiry is decay with a patina).
**Trade-offs.** Book-budget money vs risk horizon; staging effort vs cutover confidence; the IT officer's mandate vs the librarian's availability fear — the plan serves both by sequencing.
**Common mistakes.** Treating isolation as permanent (the decay argument is the case's technical core); no parallel-run (the librarian's fear becomes prophecy); dismissing either risk appetite (both are *legitimate* — the plan reconciles them); no weights (a criteria table with no weights is a list).

## PB-312 — The club treasury handover that lost everything

**Solution guide.** Failure modes, one per location: **personal cloud** — dormant-account policy locked it (ownership bound to a person's lifecycle); **laptop** — formatted (data bound to a device); **chat** — expiring history (ephemeral by design); **memory** — the verbal tour left with the treasurer. Diagnosis: "the treasurer was careless" is the wrong root cause — the *design* had no separation between the office and the officeholder; the club's data lived where a person's lifecycle could delete it. Protocol: at year-end — export chat history; consolidate current books into the **institutional society account**; produce one dated archive (zip) + a README index; record the walk-through *in writing*. Standing state (what always exists): institutional account holds current books + last 3 years' archives; handover checklist executed with the societies office copied. The deep principle: **club data must never live where a person's lifecycle can delete it — design for the role, not the officeholder.** That principle recurs (PB-408 volunteers, PB-418 fleet, PB-424 graduation) — name the recurrence.
**Alternatives.** Shared password vault for continuity (defensible; weaker than account ownership — access can be revoked, ownership can't); university-mandated handover form (policy answer — the protocol is the practice that makes the form real).
**Trade-offs.** Institutional account (continuity) vs personal convenience (the treasurer's own tooling); the archive's completeness vs the effort of compiling it — the README's 20 minutes buys decades of usability.
**Common mistakes.** "More careful handovers" (a process plea, not a design); moving data but keeping personal ownership (the dormancy lock recurs); no standing state (continuity requires *persistent* structure, not an annual scramble); blaming the graduate.

## PB-313 — The bandwidth auction (a network policy case)

**Solution guide.** Fairness must be made operational before policies can be compared — that's the case's first move. Two defensible definitions: *equal opportunity for educational use, best-effort for the rest* (mission-aligned) or *equal share, period* (simple, blunt); each implies different policies, and the choice is a value call to be argued, not derived. Evaluation: (a) flat caps — simple, transparent, but hurts light users and is easily evaded (hotspots, off-hour hoarding); (b) time-of-day shaping — matches *deferrable* demand (entertainment) to off-peak, protects peak; needs user communication or it reads as arbitrary throttling; (c) application classes — mission-aligned but **leaky**: encrypted traffic and VPNs defeat classification (the honesty note the case demands). Strong answers often combine: **(b) + scheduled lecture priority by whitelist** — deterministic (known times, known endpoints), not classification-dependent, so the live-lecture failure can't recur; whitelisting survives encryption because it doesn't classify content, it schedules capacity. Enforcement honesty: whatever the choice, *published rules* or it reads as arbitrary — a shaping policy nobody can see is indistinguishable from throttling spite.
**Alternatives.** Capacity purchase (the honest long-term fix; out of budget scope — name it); traffic quotas with rollover (variant of (a) with same bluntness).
**Trade-offs.** Educational priority vs entertainment fairness; classification elegance vs its evasion; determinism (whitelists) vs flexibility (classification) — determinism wins where failure is visible and scheduled.
**Common mistakes.** "Fair" left undefined (then any policy can be defended); app-classification trusted with encryption (the leak unexamined); no enforcement honesty (rules unpublished = arbitrary throttling); picking (a) for simplicity without pricing its harm to light users.

## PB-314 — The dataset that changed meaning mid-project

**Solution guide.** Threats, mechanism each: (1) **location change breaks spatial comparability** — the "improvement" may be a sensor placed upwind/parkside vs kerbside; the 30% could be geography, not policy; (2) **model change breaks instrument comparability** — different sensors read different distributions even co-located; (3) **trend claims conflate policy effect with measurement change** — the draft conclusion attributes to policy what the change note explains. Redesign, salvaging honestly: restrict headline analysis to **overlap windows** (both sensors running — the gold comparability window), use neighbouring cities as control series, report **both raw and break-adjusted** series, limitations stated prominently. The defensible claim, calibrated: "a change coinciding with the sensor transition is observed; attribution to policy is not supported by comparable measurements." Claim calibration *is* the grade — the evidence now supports observation, not attribution. The meta-note: the change note was legitimate metadata that *discoverability* buried — flag that as a data-quality finding the city should fix, because the next team will nearly miss it again.
**Alternatives.** Abandon the project (wastes the salvageable overlap analysis — proportionate response beats abandonment); re-run with new sensors (excluded — no new deployment allowed).
**Trade-offs.** Analytical richness (using all two years) vs comparability (using only overlap) — the honest answer sacrifices scope for validity, visibly; the team's draft-conclusion investment vs the calibrated claim.
**Common mistakes.** Reporting the 30% as a finding with a limitations footnote (the conflation *is* the claim — footnotes don't fix headline attribution); assuming the buried note was deliberate deception (it was poor discoverability — different problem, different fix); no overlap-window analysis (the one method the scenario hands you); over-retreating to "no conclusion at all" (calibration has a floor and a ceiling).

## PB-315 — The password policy that made everything worse

**Solution guide.** Harm map, requirement → mechanism → behaviour: **60-day rotation** → predictable increments (users won't invent new passwords on schedule, they'll transform old ones) → Winter2026!, Winter2027!; **four character classes** → users satisfy classes with predictable transforms (capital first, symbol last) → patterned passwords that *look* strong and crack like weak ones; **no reuse of last 12** → the memory burden spills over → cross-site reuse on *external* sites (the institution export its risk); **the combination** → total burden exceeds memory → sticky notes. Replacement (evidence-anchored, NIST SP 800-63B class): long passphrases, unique per site, **no scheduled rotation** (rotate on evidence of compromise), MFA everywhere (absorbs far more risk than rotation ever prevented), breached-password screening at set (blocklist checking exists in common systems). The defence against "we'd look soft": reframe the metric — the old policy optimizes *compliance optics* (auditable rules), the redesign optimizes *attacker cost* (breached-list checks, uniqueness, MFA — the things attacks actually meet); attackers don't brute-force a 90-day-old passphrase, they buy it from a breach dump — policy should aim where attacks aim. The honest limit: change needs leadership sponsorship and a transition plan; name it.
**Alternatives.** Password-manager mandate (the system-level fix — defensible if the institution provides one); phased rotation-removal (politically smoother — same destination).
**Trade-offs.** Compliance optics vs real security (the case's central reframe); help-desk load (short-term, during transition) vs reset-flood status quo (permanent); user burden vs policy legibility.
**Common mistakes.** "Users are the problem" (the policy *manufactured* the workarounds — mechanism, not morality); replacing rotation with "longer rotation" (misses the mechanism entirely); no MFA in the redesign (the single highest-leverage element, omitted); dismissing leadership's fear instead of addressing it with the optics reframe.

## PB-316 — The family history project and the 40-year-old disk

**Solution guide.** Triage by *loss risk*, not age: **film first** — chemical degradation is time-critical and a commercial development service exists (the one-shot medium with a clock running); **the dead-port phone** — data extraction via repair or chip-level service is specialist; honest boundary: name it specialist, don't DIY a one-shot; **Zip disk** — sudden-death failure class (known click-of-death) → image it now if a drive can be found; **floppies** — stable-ish but drives are the bottleneck; **paper photos** — stable, scan last at chosen resolution. Capture honesty: DIY (floppy/Zip imaging with obtainable drives, photo scanning) vs specialist (film lab, phone board repair) — the *identification* of which is which is the graded skill, not the prices. Output archive: open formats, a plain-text inventory with context (who/what/when/where — the README *is* the preservation, PB-312's lesson at decades scale), 3-2-1 copies, and a **named successor owner**. The meta-lesson: every archive is a future handover unless designed not to be — rescue and *succession* are the same design.
**Alternatives.** Professional archival service for everything (defensible if budget exists — the case says student budget, so triage decides what's DIY); incremental rescue (one medium per month — viable if the film goes first; triage *is* the schedule).
**Trade-offs.** DIY cost vs specialist certainty (the boundary call is the case); time pressure (film's clock) vs thoroughness elsewhere — triage resolves it; consent (the relative's records) vs family enthusiasm — permission precedes digitization for personal content.
**Common mistakes.** Ordering by age ("oldest first" — the film is *newer* and more urgent: degradation, not nostalgia, sets priority); attempting the one-shot media DIY (chip-off and film are specialist — saying so *is* the answer); no inventory/context (the rescued files become the next orphaned archive); no successor named (the rescue recurs in 20 years).

## PB-317 — The lecture-recording consent standoff

**Solution guide.** Harm map (four, including the non-obvious): **direct capture** (voice/face of questioners); **absence-as-signal** — the student who's visibly *missing* from the recording is marked as the questioner: cutting questions *creates* this harm while fixing the first; **inference** — disclosures in questions (health, caring duties, immigration status) reveal more than their content; **scope creep** — recordings reused beyond the course (next year, marketing) beyond the original consent context. Evaluation of the proposed mitigation: cutting questions reduces direct capture but manufactures the absence-signal — a partial fix that *shifts* harm to the most vocal (and thus most exposed) students. Architecture: **pause-and-resume for all Q&A** (everyone's gap, untargeted — absence becomes uninformative); **audio-only alternative channel** (reduces visual exposure); **day-one explanation** of the design; **stated retention limit**; **opt-out-of-appearing available to all** (normalized gaps — dignity by design, not exception). Access preserved because content recording continues; dignity preserved because the gap reveals nothing.
**Alternatives.** No recording (fails the access faction — their need is legitimate too); audio-only recording entirely (defensible — weaker for visual content, dignified by default; a strong answer might choose it).
**Trade-offs.** Access vs dignity — the architecture threads it by making gaps uninformative rather than choosing a side; instructor flow (pauses) vs recording continuity (a pause is a sentence of silence — acceptable).
**Common mistakes.** Fixing only direct capture (the absence-signal is the case's distinctive harm — miss it and the design repeats the failure); treating consent as a checkbox (it's architecture — who can be inferred from what's recorded *and* what's missing); no retention limit (scope creep unbounded); token access ("watch it in the office" fails the commuting/illness need).

## PB-318 — The hospital's tablet rollout (conceptual)

**Solution guide.** Measurement plan — per role, never averaged: time-per-note **by role** (the nurses' slow-down claim is testable only disaggregated — averaging it into doctor enthusiasm is precisely the aggregation erasure L26 teaches); error/omission rates in notes by role; login-frequency counts (the friction is the *claim's* mechanism — count it); patient-facing privacy incidents (zero-tolerance class). Tensions analyzed: **security vs flow** — per-room re-login is the friction's source; proximity-based re-auth or longer session windows trade security for flow, and the *trade must be named*, not assumed; **cleaning-as-security** — the hygiene regime is also an availability constraint (tablets in cleaning isolation aren't charting) — a tension the pilot's enthusiasm never surfaced. Three go/no-go criteria set *in advance* (pre-hoc, so enthusiasm can't reinterpret results): "no role's task time worsens >10%", "privacy incidents = 0", "cleaning compliance measurable and ≥ target". The erased-stakeholder framing: averages would have erased the nurses — the same aggregation ethics as PB-209, at institutional scale; naming that recurrence is the expert move.
**Alternatives.** Role-specific deployment (tablets for doctors, fixed stations for nurses — a legitimate *outcome* of the disaggregated data, not a premise); hardware-key authentication (attacks the friction directly — a design input, not a verdict).
**Trade-offs.** Security (re-auth per room) vs flow (the nurses' time) — solvable by authentication design, but the price must be stated; enthusiasm vs evidence — the pre-hoc criteria are the antidote.
**Common mistakes.** Averaging across roles (the case's core trap — the mean hides the finding); criteria set *after* results (enthusiasm writes the conclusion); no privacy metric (shoulder-surfing risk unmeasured); treating the slow-down as complaint rather than claim (it's *testable* — that's the redesign).

## PB-319 — The open-source dependency you didn't choose

**Solution guide.** Criteria table including the row weak answers omit — **risk over 12 months**: (a) freeze — works today, but unmaintained plugins accrue security holes as the *platform* evolves (the CMS updates; the plugin doesn't follow); its risk curve *rises*; (b) fork — control, but needs skills they lack and creates a *second* maintenance burden (forks inherit all future work); (c) migrate — cost now, a maintained future; (d) commercial replacement — cost per year, support contract, lowest skills demand. Recommendation varies with the argued skills reality — commonly **(c) staged migration** (or (d) if revenue justifies); freeze is defensible *only with a sunset date* ("reassess by March; migrate if no maintainer appears") — a freeze without expiry is decay with a calendar excuse. Monitoring, three signals designed to catch the *next* dependency early: release/commit cadence (quiet quarters precede abandonment), platform-compatibility advisories (does the plugin track the CMS's release cycle?), security-announce subscription. The distinction to name: **popularity is not maintenance** — 40k downloads don't fix bugs; download counts measure adoption, not stewardship.
**Alternatives.** (b) fork (defensible if a junior wants the growth — but the agency's need is reliability, not a training program); do-nothing (the risk curve answers it).
**Trade-offs.** Migration cost now vs rising freeze risk; fork control vs fork burden; commercial cost vs self-reliance — every option pays, the criteria decide *which currency*.
**Common mistakes.** "It works today" as the criterion (the case's central trap — the risk is time-decaying, and "today" is its most misleading unit); popularity read as maintenance; no monitoring design (the next dependency arrives unannounced, again); no sunset on the freeze (indefinite decay).

## PB-320 — The translation model in the university clinic (conceptual)

**Solution guide.** Accuracy critique: **85% average is the wrong number because the error distribution, not the mean, decides safety** — if the 15% concentrates in drug names, doses, and allergies (the high-consequence set), the tool is unusable for intake regardless of the average; benchmarks aggregate sentence types, hiding exactly the concentration that matters. **Consequence asymmetry** completes it: a mistranslated hobby is cosmetic; a mistranslated allergy is catastrophic — so per-category metrics (especially the high-consequence set) are the only meaningful evaluation. Deployment constraints (three): **scope limitation** — triage/orientation only, *never* clinical facts without human verification; **mandatory human confirmation** for the high-consequence set (allergies, medications, conditions — a checklist the clinician verifies, not a vibe); **visible failure-honesty** — signage stating what the tool may and may not be trusted for, plus a staff escalation path. Community measurement, *with* not *about*: co-designed error taxonomies (which mistakes matter, named by speakers), a speaker panel reviewing real (anonymized) usage, a grievance channel. The baseline honesty: the no-interpreter status quo has its own harm — the comparison is against current reality, not perfection; the tool may still win *even with* its limits.
**Alternatives.** Wait-for-budget (defensible if the status quo's harm were mild — the case says it isn't); phone-based remote interpreting (the actual industry middle path — worth naming as the obvious question the clinic should price).
**Trade-offs.** Access now (the tool helps where no interpreter exists) vs safety floor (the confirmation layer's friction); average metrics (vendor's frame) vs error-distribution metrics (safety's frame) — the case is the conflict between those frames.
**Common mistakes.** Arguing from the average either way (both "85% is great" and "85% is unsafe" miss the distribution question); no human-confirmation layer (the high-consequence set floats unsupervised); community as subject not evaluator (consultation theatre); pretending the tool must be perfect (the baseline is *current reality* — the honest frame).

## PB-321 — The energy dashboard that changed behaviour (and then didn't)

**Solution guide.** Diagnosis — three candidate mechanisms, each with its discriminating test: **novelty decay** (passive displays fade — test: did usage rise again after re-engagement events? if the decay pauses at interventions, novelty); **confounds** (weather/exams — test against weather-normalized data and non-pilot dorms: if control dorms show the same curve, it's season, not novelty); **feedback absence** (the display shows numbers but no *actionable loop* — no floor goal, no comparison, no "what do I do with this?" — test: interview residents; if they never knew what to *do*, the display was information without agency). Evaluation of "expand": the recommendation replicates the *input* (another display) without addressing the *mechanism* — it will replicate the decay too; expansion satisfies the office's need to act while solving nothing. Intervention targeting the mechanism: **social comparison with a light goal** (floor-vs-floor — floors respond to each other), **actionable framing** ("tonight vs your floor's average tonight" — a number you can move), **periodic re-engagement** (novelty is renewable with effort, not permanent). Honest boundary: behaviour effects are hard to sustain — set the *measurement plan before* expansion so the next report can't fool itself either.
**Alternatives.** Kill the dashboard (defensible if interviews show zero actionable engagement — but the measurement plan should decide, not the anecdote); individual-level feedback (privacy and metering costs — floor-level is the honest scale).
**Trade-offs.** Visibility (dashboards are cheap and legible) vs efficacy (they decay) — re-engagement is the maintenance cost of visibility; advocacy (the office wants wins) vs measurement honesty — the pre-committed plan protects both.
**Common mistakes.** Accepting the decay as "dashboards don't work" (the mechanism is un-diagnosed — decay, confound, and feedback-absence have *different* fixes); expansion-as-default (the report's recommendation reproduced its input); no control comparison (confounds masquerade as decay); post-hoc measurement plan (the next report inherits the same self-deception).

## PB-322 — The accessibility retrofit deadline

**Solution guide.** Evaluation: "fix everything" fails **effort realism** — three weeks, one developer, and a big-ticket keyboard-nav rewrite usually delivers nothing *finished* (the worst outcome: nothing ships, nothing is communicated); the developer's plan is **impact-ordered** but its ethics hang on the *communication* component — partial fixes are acceptable when *published* and paired with an alternative access path; undisclosed partial remediation is just exclusion with a schedule. Recommendation: the developer's plan **plus** the two quick wins done immediately (form labels and text-status are cheap-and-high-impact — they're non-negotiable even in a constrained plan because they serve everyone now), plus a *stated schedule* for the keyboard nav. Regression guard, two mechanisms: automated accessibility checks in the project's test routine (the repo's own validator culture, applied — checks run on every change, so fixed things stay fixed) and a **manual screen-reader pass per release** (automation misses the experiential layer). The principle: **accessibility is maintenance, not a one-time audit** — the guard is what makes that true.
**Alternatives.** Fix-everything (defensible if the quiz viewer's rewrite would take three weeks anyway — check the estimate, don't assume); outsource the retrofit (budget reality probably forbids; name it if proposing).
**Trade-offs.** Breadth (everything half-fixed) vs depth (the highest-use path fully fixed) — impact-ordering decides; speed vs the communication duty — the known-issues notice is what reconciles them.
**Common mistakes.** "Fix everything" with nothing shipped (realism failure); partial fixes with no published known-issues (exclusion with a schedule); quick wins deferred (they cost a day and serve everyone — deferral is pure loss); no regression guard (the next sprint re-breaks the labels — accessibility debt resumes compounding).

## PB-323 — The dual-supplier cloud dilemma

**Solution guide.** Evaluation with each plan's *own* failure mode named: (a) full multi-cloud — maximum protection, but for a small team the doubled operational surface (skills, incidents, cost) **becomes the outage source**: its failure mode is *chronic* (the reliability tax is paid daily); (b) warm standby — strong data durability; its failure mode is *the stale standby* (untested failover rots silently — the backup that's never been asked to work, PB-213's lesson at infrastructure scale); (c) fast-exit plan — cheapest; its failure mode is *plan rot* (unrehearsed exits take days, not hours; egress costs quietly block the exit — the plan decays into a document). Recommendation: **(b) + (c) hybrid** — standby for data durability, rehearsed-exit for runtime continuity, with **failover drills scheduled quarterly** (the drill is what keeps the standby from rotting). The accepted-risk statement for the board, in one sentence: "brief (minutes-to-hours) runtime loss during regional outages is accepted; total data loss and multi-day exit are designed against." Naming what's accepted is the senior move — the board can govern a named risk, not a vague promise.
**Alternatives.** (a) full multi-cloud (defensible at larger scale/team — the complexity tax scales down with headcount; say so); (c) alone (defensible if the board accepts hours-long runtime loss explicitly — put it in the risk register, not the footnotes).
**Trade-offs.** Cost vs protection at every rung; complexity vs resilience (the startup's paradox: the cure can kill the patient); the board's "no SPOF" mandate vs its literal infeasibility — the accepted-risk statement is how a professional says "no" to an absolute.
**Common mistakes.** Multi-cloud by mandate (the board's phrase adopted as architecture — the complexity tax unpriced); standby deployed and never failed-over (the rot — untested until it's needed, exactly when testing is impossible); no accepted-risk statement (the recommendation reads as complete protection, which no option provides); no drill schedule (plans rot — schedule is the antidote).

## PB-324 — The course-recommendation algorithm (conceptual)

**Solution guide.** Claim analysis, mechanism not slogan: "bias-free because it uses only grades" fails because **grades encode everything they correlate with** — prior schooling quality, programme sorting, advice networks — so the model produces correlated outputs without ever *seeing* a protected attribute; removing the attribute from inputs doesn't remove it from the *history the features carry*. "Only grades" is a claim about inputs; bias lives in what inputs *mean*. Fairness evaluation, populations not averages: **recommendation diversity by cohort** (aggregate, privacy-respecting — do first-generation students receive systematically narrower suggestion sets?), **outcome follow-up** (do recommended electives yield grades/satisfaction comparable to self-chosen ones — the tool's value test, not just its fairness test), **subgroup performance gaps** (aggregate only). Three pilot rules: **exploration floor** (some non-programme suggestions always included); **easy opt-out**, honoured; **no gating** (advice only — the moment it touches registration capacity, it allocates opportunity); plus **per-term aggregate fairness reporting**. The satisfied majority is honoured by keeping the tool *advisory* — the dean's ask is constraints, not cancellation.
**Alternatives.** Kill the pilot (defensible if the diversity data is bad — but the rules give the pilot a chance to earn trust); extend faster (vendor pressure — the rules exist precisely to resist this).
**Trade-offs.** Exploration breadth (the dean's value) vs personalization precision (the satisfied majority's experience) — the floor trades a little precision for structural openness; innovation pace vs fairness evidence — the rules sequence them.
**Common mistakes.** Accepting or rejecting the vendor claim as a slogan (mechanism, not vibes — *why* grades carry the bias is the answer); averages across cohorts (the erasure pattern again); no outcome follow-up (fairness measured without value measured = a policy, not a pilot); opt-out offered but hard (honoured-on-paper is the classic implementation failure).

## PB-325 — The club's old projector and the new lecture

**Solution guide.** Diagnoses, mechanism each: **dim image** — lamp age (8 years is far past lumen half-life for most lamp technologies) × hall size × ambient light: a projector that filled a small room cannot light a 150-seat hall; the small-room test couldn't see it because *none* of the variables were present. **Washed colours** — aged lamp spectrum (phosphor degradation shifts colour) + screen surface (a hall wall is not a matte screen); **HDMI handshake failure** — cable/version/EDID negotiation: transient, classic, solved by *tested spares* and a second device rehearsed. Testing protocol, venue-realistic: test **in the venue** at talk-time lighting, full-sized content, viewed from the back row, spare cable + second laptop rehearsed — the small-room test didn't merely under-inform, it *actively misled* (it validated the equipment in conditions that don't transfer; a false pass is worse than no test). Committee decision with criteria: venue variability is the decisive criterion — an owned projector doesn't fix a *new* hall's lighting; the **protocol travels, the hardware doesn't** → protocol + keep borrowing (rental-quality loans per event), not the purchase.
**Alternatives.** Buy a mid-range projector (defensible if the society lectures in the *same* hall weekly — venue variability then collapses and ownership wins); rental upgrade per event (the protocol plus budget — fine where stakes justify).
**Trade-offs.** Ownership (predictable equipment, storage burden, same hall trap) vs protocol (portable skill, depends on loan quality); test-time investment vs event-night risk — the protocol is one hour of rehearsal against a public failure.
**Common mistakes.** "Never borrow old projectors" (lamp age mattered *in that hall* — the rule confuses instance with cause); buying hardware to fix a protocol failure (the venue trap); no back-row test in the protocol; no spare-cable ritual (the handshake failure was the most preventable of the three).
